# VoxLocal Windows — аудит архитектуры и вставки

Дата аудита: 2026-09-28
Ветка: `windows-port`

## 1. Текущий конвейер

```text
Program.Main
  → SettingsStore / TranscriptionHistoryStore / services
  → GlobalHotkeyService
  → DictationController
  → AudioRecorder
  → SherpaTOneTranscriber или WhisperTranscriber
  → OllamaRefiner (текущий refinement)
  → TranscriptionHistoryStore
  → TextInserter
  → OverlayWindow / TrayController
```

### Запуск и жизненный цикл

- `Program.cs` создаёт WPF-приложение с `ShutdownMode.OnExplicitShutdown`.
- Используется mutex `VoxLocal.Windows.SingleInstance`, поэтому одновременно работает один экземпляр.
- Глобальный low-level keyboard hook устанавливается через `GlobalHotkeyService`.
- `DictationController` подписывается на события нажатия/отпускания основной клавиши и Escape.
- Сервисы записи, Sherpa и контроллер освобождаются через `using`/`Dispose`.

### Состояния диктовки

`DictationStateMachine` контролирует переходы:

```text
Idle → Preparing → Recording → Stopping → Transcribing
                                      → Refining (если включён)
                                      → Inserting → Completed → Idle
```

При отмене или ошибке конвейер возвращается в `Idle` после задержки.

## 2. Настройки и данные

- Настройки: `%LOCALAPPDATA%\VoxLocal\settings.json`.
- История: `%LOCALAPPDATA%\VoxLocal\history.json`.
- Лог: `%LOCALAPPDATA%\VoxLocal\logs\voxlocal.log`.
- Модели: `%LOCALAPPDATA%\VoxLocal\models\`.
- `SettingsStore.Save()` использует временный файл и замену, что снижает риск повреждения JSON.
- Текущая модель refinement — `OllamaRefiner`; она разрешает только loopback endpoint и не поддерживает облако.
- В текущем UI refinement представлен только как локальная Ollama.

## 3. Что уже реализовано

- Режим удержания клавиши и режим переключения.
- Основная комбинация Alt+Space и альтернативный режим Ctrl+Alt+Space.
- Отмена записи через Escape.
- Локальное распознавание Sherpa-ONNX и Whisper.
- Удаление временного WAV после обработки.
- История последних пяти успешно обработанных текстов.
- Копирование текста в буфер.
- Автоматическая вставка через Ctrl+V.
- Unicode-ввод для Sublime Text и Termius.
- Обнаружение защищённого поля через UI Automation.
- Сохранение и восстановление предыдущего буфера с проверкой sequence number.
- Режим «только копировать».
- Базовая защита ответа refinement в `RefinementSafeguard`.
- 10 консольных тестов, все проходят.

## 4. Подтверждённые точки риска вставки

### 4.1 Отправка вставки и фактический результат

`SendInput` подтверждает только принятие структуры ввода Windows, но не факт изменения текста в целевом редакторе. Для обычных приложений это может выглядеть как успешная вставка даже при игнорировании Ctrl+V.

**План:** сохранять текст в истории и оставлять его в буфере как fallback; улучшить статус и повторную вставку. Не обещать абсолютное подтверждение для произвольного приложения.

### 4.2 Фокус целевого окна

Окно захватывается в начале записи. Перед вставкой код пытается вернуть его на передний план и ждёт 180 мс. Если окно не стало foreground, операция переводится в `ClipboardOnly`.

**План:** сохранить диагностические данные процесса/окна, проверить задержки и дать пользователю повторную вставку.

### 4.3 Модификаторы горячей клавиши

Основная клавиша перехватывается low-level hook, а обработчики вызываются через `Dispatcher.BeginInvoke`. Обработка распознавания запускается асинхронно (`_ = StopAndProcessAsync()`), поэтому отпускание физической клавиши и отправка Ctrl+V разделены длительным конвейером, но отдельного явного ожидания всех модификаторов непосредственно перед вставкой нет.

**План:** проверить состояние Alt/Ctrl/Shift перед синтетическим вводом и добавить безопасную задержку/повтор только после тестирования.

### 4.4 Буфер обмена

Текущая схема:

1. снять snapshot всех доступных форматов;
2. записать текст;
3. проверить foreground;
4. отправить вставку;
5. через 5 секунд восстановить старый буфер, только если sequence number не изменился.

Риск: разные приложения и clipboard managers могут читать буфер с задержкой или удерживать его. Текущий код уже защищает пользовательское последующее копирование, но не делает несколько попыток записи.

**План:** тестировать конфликт буфера и при необходимости добавить retry с ограничением.

### 4.5 Повышенные права

Если целевое приложение запущено с более высоким уровнем прав, Windows UIPI может блокировать синтетический ввод. Код уже оставляет текст в буфере при неудаче фокуса, но отдельного определения elevated target нет.

**План:** добавить понятную диагностику и инструкцию, не пытаться обходить защиту Windows.

### 4.6 Пустой результат

`DictationController` передаёт `transcript.Text` дальше без отдельной проверки на пустую строку. `TextInserter` в этом случае возвращает `ClipboardOnly`, не вставляя текст, но пользователь может получить неочевидный результат.

**План:** отдельный статус пустой диктовки, отсутствие запроса к LLM и отдельный тест.

### 4.7 Ошибки refinement

Ошибка refinement сейчас логируется как `Refinement skipped`, после чего используется исходный текст. Это правильный fallback. Однако тип refinement привязан к Ollama, а таймаут ограничен настройкой в секундах и не имеет облачного профиля.

**План:** сохранить fallback-поведение при замене реализации на универсальный провайдер.

## 5. Ограничения текущего аудита

- Фактическое поведение с конкретными приложениями требует ручного Windows-тестирования.
- Невозможно гарантировать определение фактического изменения текста в каждом редакторе через общий Win32 API.
- Проблемы с elevated-приложениями зависят от уровня прав процесса и политики Windows.
- Нельзя проверить облачную модель до добавления кастомного провайдера.

## 6. Приоритеты реализации

1. Не ломать текущий режим без refinement.
2. Добавить диагностические логи без пользовательского текста и секретов.
3. Улучшить пустой результат и fallback-вставку.
4. Заменить Ollama-специфичный refinement на OpenAI-compatible provider.
5. Добавить настройки кастомного Base URL, модели и ключа.
6. Добавить облачный clean-text режим с исходным текстом как обязательным fallback.
7. После этого провести ручные тесты вставки и облачной обработки.
